# ИС «Городская Дума»

Информационная система управления деятельностью городской Думы.  
Автоматизация учёта депутатов, комиссий, заседаний и посещаемости заседаний.

---

## О проекте

**ИС «Городская Дума»** - учебный проект, выполненный в рамках дисциплины  
«Методология и практики DevOps» (Московский Политех, направление 10.03.01  
«Информационная безопасность»).

**Предметная область:** работа городской Думы - депутаты, комиссии,  
заседания и посещаемость заседаний.

**Назначение:** автоматизация учёта депутатов, комиссий, заседаний  
и посещаемости.

**Тип приложения:** Web-приложение с HTTP API и реляционной базой данных.

## Быстрый старт

### 1. Клонирование репозитория

```bash
git clone https://github.com/gorodskaya-duma241-351.git
cd gorodskaya-duma241-351
```

### 2. Настройка окружения backend

Создайте виртуальное окружение и установите зависимости:

```
cd backend
python -m venv .venv

# Windows
.venv\Scripts\activate

# Linux / macOS
source .venv/bin/activate

pip install -r requirements.txt
```

### 3. Конфигурация `.env`

Скопируйте `.env.example` в `.env` и заполните значения:

```
cp .env.example .env
```

Пример содержимого `.env`:

```
SECRET_KEY=your-super-secret-key-change-me
DATABASE_URL=sqlite:///./duma.db
```

> Файл `.env` **не должен** попадать в Git. Он уже добавлен в `.gitignore`.

### 4. Запуск backend

```
uvicorn main:app --host 127.0.0.1 --port 8001 --reload
```

- **API:** [http://127.0.0.1:8001](http://127.0.0.1:8001/)
- **Swagger:** [http://127.0.0.1:8001/docs](http://127.0.0.1:8001/docs)
- **Health:** [http://127.0.0.1:8001/api/health](http://127.0.0.1:8001/api/health)

База данных и таблицы создаются автоматически при первом запуске.

### 5. Запуск frontend

В отдельном терминале:

```
cd frontend
python -m http.server 5500
```

Откройте браузер: **[http://127.0.0.1:5500](http://127.0.0.1:5500/)**

## Модель данных

В системе **6 таблиц**:

| Сущность | Поля |
|---|---|
| `User` | `id`, `username`, `password_hash`, `role` |
| `Deputy` | `id`, `full_name`, `party`, `district` |
| `Commission` | `id`, `name`, `description`, `chairman_id` |
| `DeputyCommission` | `deputy_id`, `commission_id` |
| `Meeting` | `id`, `commission_id`, `title`, `date`, `location` |
| `Attendance` | `id`, `meeting_id`, `deputy_id`, `status` |

**Связи:**

- `Commission.chairman_id` -> `Deputy.id`
- `Meeting.commission_id` -> `Commission.id`
- `Attendance.meeting_id` -> `Meeting.id`
- `Attendance.deputy_id` -> `Deputy.id`
- `DeputyCommission` - связь многие-ко-многим между `Deputy` и `Commission`

---

## Бизнес-правило

> **Один депутат не может иметь две записи посещаемости одного и того же заседания.**

Реализовано двумя способами:

1. **На уровне API** - перед созданием записи выполняется проверка.
При повторном добавлении возвращается **HTTP 400**
с сообщением: `"Для этого депутата уже есть запись посещаемости"`.
2. **На уровне БД** - ограничение `UNIQUE(meeting_id, deputy_id)`.

## Обработка ошибок

| Код | Значение |
|---|---|
| −200 | Успешная операция |
| −400 | Некорректная операция / дубликат |
| 401 | Отсутствует или недействительна авторизация |
| 404 | Объект не найден |

**Примеры:**

- `DELETE` несуществующего депутата -> **404**
- Защищённый endpoint без токена -> **401**
- Повторная посещаемость -> **400**

## Правила внесения изменений

Любое изменение в приложении (backend, frontend, конфигурация, БД)
считается внесённым только после прохождения проверок ниже.

### Обязательные команды проверки

Выполняются **перед каждым коммитом** и **перед сдачей работы**.

**1. Проверка синтаксиса backend**

```bash
cd backend
python -m compileall .
```

Ожидаемый результат: ошибок нет, команда завершается с кодом `0`.

**2. Запуск backend**

```bash
cd backend
uvicorn main:app --host 127.0.0.1 --port 8001 --reload
```

Ожидаемый результат: сервер стартует без исключений, в логе видно
`Application startup complete`.

**3. Проверка доступности сервиса**

```bash
curl http://127.0.0.1:8001/api/health
```

Ожидаемый результат:

```json
{ "status": "ok" }
```

**4. Проверка API через Swagger**

Открыть в браузере: `http://127.0.0.1:8001/docs`

Проверить вручную по порядку:

1. `POST /api/auth/register` — создать пользователя.
2. `POST /api/auth/login` — получить `access_token`.
3. Нажать **Authorize** и вставить `Bearer <token>`.
4. `POST /api/deputies` — создать депутата.
5. `GET /api/deputies` — депутат присутствует в списке.
6. `POST /api/commissions` — создать комиссию с председателем.
7. `POST /api/meetings` — создать заседание для комиссии.
8. `POST /api/meetings/{id}/attendance` — добавить посещаемость.
9. Повторно вызвать тот же endpoint с тем же депутатом —
   ожидается **HTTP 400** и сообщение
   `"Для этого депутата уже есть запись посещаемости"`.
10. `GET /api/meetings/{id}/attendance` — запись отображается.
11. `DELETE /api/deputies/{id}` — удалить депутата.
12. Повторно `DELETE /api/deputies/{id}` — ожидается **HTTP 404**.

**5. Запуск frontend**

```bash
cd frontend
python -m http.server 5500
```

Открыть `http://127.0.0.1:5500` и убедиться, что интерфейс загружается
и обращается к backend без ошибок в консоли браузера (F12 → Console).

### Запрещённые действия

В приложении **нельзя**:

- редактировать файл `backend/duma.db` вручную (любые изменения схемы
  и данных — только через ORM и API);
- создавать записи посещаемости в обход API (прямым `INSERT` в БД) —
  это обходит проверку бизнес-правила;
- отключать или удалять ограничение `UNIQUE(meeting_id, deputy_id)`
  и проверку дубликата на уровне API;
- хранить пароли в открытом виде — только bcrypt-хеш;
- задавать `SECRET_KEY` значением по умолчанию
  (`your-super-secret-key-change-me`) в рабочем `.env`;
- удалять или переименовывать `.env.example`;
- менять порты по умолчанию (`8001` для backend, `5500` для frontend)
  без одновременного обновления README;
- удалять или комментировать проверки существования связанных объектов
  (комиссия, депутат, заседание);
- добавлять секреты, `.env`, `duma.db` и `__pycache__` в репозиторий.

### Порядок приёмки

Приёмка выполняется на чистом клоне репозитория по шагам:

| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `cd backend && python -m venv .venv` + активация | Виртуальное окружение создано |
| 2 | `pip install -r requirements.txt` | Зависимости установлены без ошибок |
| 3 | `cp .env.example .env` | Файл `.env` создан |
| 4 | `uvicorn main:app --host 127.0.0.1 --port 8001 --reload` | Сервер запущен, БД и таблицы созданы автоматически |
| 5 | `GET /api/health` | `{"status": "ok"}` |
| 6 | `cd frontend && python -m http.server 5500` | Frontend доступен на `http://127.0.0.1:5500` |
| 7 | Регистрация и вход в Web-интерфейсе | Токен получен, интерфейс открывается |
| 8 | Добавление, просмотр и удаление депутата | Операции выполняются, список обновляется |
| 9 | Создание комиссии с председателем | Комиссия отображается с председателем |
| 10 | Создание заседания для комиссии | Заседание отображается |
| 11 | Добавление посещаемости | Запись создаётся, статус сохраняется |
| 12 | Повторное добавление того же депутата на то же заседание | **HTTP 400**, запись не создаётся |
| 13 | `DELETE` несуществующего депутата | **HTTP 404** |
| 14 | Запрос защищённого endpoint без токена | **HTTP 401** |
| 15 | Проверка `http://127.0.0.1:8001/docs` | Swagger открывается, все endpoint видны |

**Приёмка считается пройденной**, если все 15 пунктов выполнены
без отклонений. Любое отклонение оформляется как дефект и устраняется
до повторной проверки.
