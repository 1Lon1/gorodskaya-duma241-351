# Staging для ЛР6

На целевом Linux-сервере нужны Docker Engine, Compose v2, Python 3 и `flock`. Для SSH используется отдельный ключ и пользователь `duma-deploy`. Контроллер в каталоге `controller/` позволяет запустить отдельный SSH-процесс на учебной ВМ. Он слушает `127.0.0.1:12226`. Приложение доступно на `127.0.0.1:18080` и хранит SQLite в томе проекта `duma-lab6-staging`.

## Настройка целевого окружения

1. Скопируйте `release.sh`, `smoke.py`, `compose.yaml` и `ssh-command.sh` в каталог `duma-staging` пользователя `duma-deploy`. Установите для обоих скриптов `.sh` права `0755`.
2. В том же каталоге запишите в файл `registry` строку `ghcr.io/1lon1/gorodskaya-duma241-351`. Создайте `.env` с уникальным `SECRET_KEY` и `smoke.json` с ключами `username` и `password` для отдельной тестовой учётной записи API. Права обоих файлов должны быть `0600`.
3. Разрешите ключу pipeline выполнять `ssh-command.sh` через принудительную команду OpenSSH. Доступ ограничен командами `deploy <SHA>` и `rollback`. Если используется контейнер `controller/`, соберите его служебный образ с `DEPLOY_UID` владельца каталога и `DOCKER_GID` группы сокета. Подмонтируйте каталог `duma-staging` в одноимённый каталог пользователя внутри контейнера, сокет Docker в `/var/run/docker.sock` и запустите контейнер с `--network host`. В `duma-staging/ssh` положите отдельный ключ хоста `host_ed25519` и публичный ключ pipeline в `authorized_keys`. Docker-сокет даёт контроллеру доступ к демону учебной ВМ. Ключ и бинарники контроллера обслуживает администратор ВМ.
4. В GitHub Environment `staging` для `main` настройте `STAGING_SSH_HOST`, `STAGING_SSH_PORT` и `STAGING_SSH_HOST_KEY`, а приватный ключ положите в секрет `STAGING_SSH_KEY`. Значение `STAGING_SSH_HOST_KEY` — заранее сверенная строка формата `known_hosts` для адреса и порта, с которых GitHub runner обращается к SSH. Для GitHub-hosted runner нужен сетевой маршрут к SSH на ВМ.

## Запуск и наблюдение

После успешного CI с публикацией из `main` стартует `Lab6 CD Staging`. Вкладка Actions также позволяет вручную выбрать `deploy` с полным SHA или `rollback`. Права на `main` остаются под контролем существующих правил репозитория.

Сервер устанавливает образ по digest из registry, проверяет здоровье контейнера и `/version`, затем выполняет вход и цепочку создания, чтения и удаления тестового депутата. Ревизии принятого и предыдущего выпусков хранятся в `.releases`. При неуспешной проверке сервер пытается вернуть последний принятый выпуск и возвращает ошибку в Actions.

В текущем проекте откат переключает образ и сохраняет том данных. Если в будущих релизах появятся несовместимые изменения схемы БД, для них понадобится отдельный сценарий миграции и восстановления.
